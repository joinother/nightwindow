# 今夜星 · 开发前设计文档

> 版本 v0.1 · 2026-11-07
> 本文档记录"今夜星"立项前的全部设计决策、算法口径、竞品结论与待办。
> 所有结论都来自对 Sky Live、天文通两款真实产品的静态分析与接口实测。

## 1. 产品定位

### 1.1 一句话

**回答"今晚几点出门、去哪、看什么"的观星决策工具。**

不是星图，不是天文百科，不是社区。

### 1.2 目标用户

| 用户 | 需求 | 占比预估 |
|---|---|---|
| 城市观星新手 | 今晚能不能看到星星，去哪看 | 60% |
| 摄影爱好者 | 银河窗口、光污染、云量 | 25% |
| 天文爱好者 | 视宁度、行星高度角、深空目标 | 15% |

### 1.3 明确不做

- **星图/AR**：Stellarium 免费且更好，做星图是拿短板打长板
- **星图解算**：tetra3（ESA 开源）、astrometry.net 现成
- **社区/图库**：无底洞，不做
- **天文百科**：内容成本高、留存低

## 3. 核心设计原则

### 原则一：开屏即答案

打开 App 第一屏必须直接给出结论，没有引导页、没有首页层级、没有"开始使用"按钮。

### 原则二：一眼一个数，但必须可解释

主视觉是一个 0–100 的综合分 + 等级词 + **主要限制因素**。

分数不是黑箱：抽屉里必须能看到"天气分 × 天空分 = 综合分"的拆解。

### 原则三：分数必须区分目标

同一个夜晚，拍银河和拍木星是两件事。同一个分数服务不了两种需求，所以提供 **深空 / 行星 / 月面** 三档切换。

> 这是与 Sky Live、天文通最本质的差异：
> Sky Live 只有一个分数且带 0.75 死底数（晴天永远 ≥55，从不说"别去"）；
> 天文通云量权重 87，实测晴天里通透度从 0.1 拉到 0.9 只影响 3.6 分——名义上是观星指数，实际是云量预报。

### 原则四：窗口比分数重要

分数回答"值不值得"，窗口回答"几点去"。两者都要，窗口在分数正下方。

## 4. 算法设计

### 4.1 综合分

```
综合分 = 天气分 × 天空分 ÷ 100
```

乘法而非加法，理由：**两个维度都不能太差**。加法会让好天气补偿重度光污染（天文通正是这么做的：全阴天仍能拿 11 分）。

### 4.2 天气分（0–100）

```
天气分 = (0.55·云 + 0.20·通透 + 0.15·视宁 + 0.10·露点) × 大气质量系数
```

| 因子 | 计算 |
|---|---|
| **云** | 窗口内**均值**，再乘稳定度惩罚：`100×(1−c̄/100)^1.35 × (1 − 0.30×min(1, σ/25))` |
| **通透** | `transp × e^(−0.6·AOD)`，沙尘/烟霾直接压低 |
| **视宁** | `clamp((3.5 − seeing)/2.5)` |
| **露点** | `clamp(dewSpread/8)` |

> 云量用均值而不是最低值。原来的"取窗口内最好的一小时"会让分数系统性偏乐观：一个两小时的窗口里只有十分钟晴，不该给 85 分。

### 4.3 大气质量系数

目标在地平线上多高，决定穿过多少大气：

```
大气质量 X = 1 / (sin h + 0.50572·(h + 6.07995)^−1.6364)
系数 = 2.512^(−0.12·(X−1))，clamp 到 [0.45, 1]
```

| 高度角 | 大气质量 | 系数 |
|---|---|---|
| 90° | 1.0 | 1.00 |
| 40° | 1.6 | 0.94 |
| 20° | 2.9 | 0.81 |
| 10° | 5.6 | 0.66 |

> 系数取 0.12 mag/airmass 而非通用的 0.22，因为消光对面源天体（银河、星云）和点源（恒星）影响不同：面源的目标与天空背景同时被削弱，对比度损失小于点源。

### 4.4 天空分（0–100）

```
天空分 = 100 × Bortle系数 × 月光压制
月光压制 = 1 − 0.62 × 照亮比例 × 月光占窗口比例 × 月距系数
月距系数 = clamp(1 − 月距/120°, 0, 1)
```

| 目标 | Bortle 项 |
|---|---|
| 银河（深空） | `(10 − bortle) / 9` |
| 行星 | `0.60 + 0.40 × (10−b)/9` |
| 月面 | `0.72 + 0.28 × (10−b)/9` |

月距系数让"月亮离目标 30°"和"月亮在天另一侧"分成两种情况。

### 4.5 置信度（已砍）

**这个功能已从产品中移除。**

它需要两个数值模型的分歧（ECMWF vs ICON）才能算，而国内只有华为单模型。引入第二模型的代价是配额、延迟、可解释性三重成本，收益不明确。

**首屏只给一个数，不给误差范围。** 数据源与新鲜度信息放到"数据"页。

> 保留此节是为了记录「考虑过并否决」，避免以后重复讨论。

### 4.6 等级

| 分数 | 等级 |
|---|---|
| ≥ 70 | 极好 |
| 50–69 | 良好 |
| 30–49 | 一般 |
| < 30 | 差 |

### 4.7 目标体系：深空 / 行星 / 月面

**顶层三个模式，深空内部再选具体目标。**

| 模式 | 代表目标 | 候选 |
|---|---|---|
| 深空 | 当夜**分数最高**的那个 | 仙女座 M31、猎户座 M42、昴星团 M45、银河中心 |
| 行星 | 土星 | 后续扩展为木星/火星各自窗口 |
| 月面 | 月亮（本地星历） | — |

**为什么顶层用「深空」而不是「银河」：**

1. **银河只是深空的一个目标**，且季节性极强——11 月初银心 19:00 才 14°、21 点就落下，一年里有大半年晚上根本拍不到
2. **用户真正能拍的东西随季节变**：深秋是 M31，冬天是 M42，夏天才是银河
3. **可解释**："深空 63 分（仙女座 M31，高度 80°）"比"深空 63 分"有用得多

代价是用户不知道"最佳目标"怎么选的，所以**界面上必须写出目标名**。

### 4.8 最佳窗口（按目标分别计算）

| 目标 | 约束 |
|---|---|
| **深空** | 天文夜 ∩ 无月 ∩ 云 ≤ 45% ∩ **目标高度 > 10°** |
| **行星** | 云 ≤ 45% ∩ **目标高度 > 15°** |
| **月面** | 月升之后 ∩ 云 ≤ 45% ∩ **月亮高度 > 5°** |

取满足条件的**最长连续时段**。

**实测（11/7 同一晚）**：

| 地点 | 模式 | 分数 | 窗口 | 限制 |
|---|---|---|---|---|
| 成都（Bortle 8） | 深空 · M31 | **14** | 19:00–01:00 | 光污染 |
| 成都 | 行星 · 土星 | **42** | 19:00–01:00 | 视宁 |
| 成都 | 月面 | — | 今晚没有（月亮 06:30 才升） | — |
| 冷湖（Bortle 1） | 深空 · M31 | **63** | 19:00–01:00 | 视宁 |

> 对比：如果把深空模式绑死成"银河"，成都只有 **9 分**、冷湖 **39 分**、窗口各只剩 1 小时——因为银心当晚 19:00 才 14°。换成"当夜最佳目标"后，同一晚的 M31 在 79° 高空，分数和窗口都反映了真实可拍性。

## 5. 天文计算口径

### 5.1 月相绘制

按月龄真实计算明暗界线，**必须区分盈亏方向**：

```
相位角 θ = 2π × (月龄 / 29.53)
照亮比例 f = (1 − cos θ) / 2
明暗界线半轴 a = r × |cos θ|

盈月（月龄 < 14.77）：亮面在右
亏月（月龄 > 14.77）：亮面在左
```

用多边形拟合边界（limb 圆弧 + 椭圆弧），不用两个圆叠加（后者界线形状是错的）。

### 5.2 Bortle ↔ 天顶亮度 ↔ 肉眼极限星等

| Bortle | 天顶亮度 (mag/arcsec²) | 极限星等 | 银河 |
|---|---|---|---|
| 1 | 21.85 | 7.8 | 清晰，暗星云可辨 |
| 2 | 21.60 | 7.3 | 清晰 |
| 3 | 21.35 | 6.8 | 明显 |
| 4 | 20.80 | 6.3 | 明显 |
| 5 | 19.70 | 5.8 | 隐约 |
| 6 | 18.80 | 5.3 | 隐约，需避月光 |
| 7 | 18.20 | 4.8 | 不可见 |
| 8 | 17.80 | 4.3 | 不可见 |
| 9 | 17.00 | 3.8 | 不可见 |

> ⚠️ 常见错误：把 Bortle 8 写成 21.4 mag（那是 Bortle 3–4 的亮度）。

### 5.3 天文夜

太阳高度角 < −18° 的时段。成都 11 月上旬约 19:02–05:48，**不是 18:42**（那是民用暮光）。

### 5.4 银河窗口

三个条件同时满足：

```
银心高度角 > 10°
太阳高度角 < −18°
月亮在地平线下
```

11 月初在成都，银心约 21:20 落下（每天提前约 4 分钟，恒星日效应）。


### 5.5 月光高度角（已实现）

月亮的压制不是"升起来就扣分"，而是随**高度角 × 照亮比例**连续变化。

**星历**（Meeus 简化式，本地计算，误差 < 0.3°）：

```
平黄经 Lp、平距角 D、太阳平近点角 M、月亮平近点角 M'、升交点角距 F
黄经 λ = Lp + 6.289 sin M' − 1.274 sin(2D−M') + 0.658 sin 2D
            + 0.214 sin 2M' − 0.186 sin M − 0.114 sin 2F
黄纬 β = 5.128 sin F + 0.281 sin(M'+F) − 0.278 sin(F−M') − 0.173 sin(2D−F)
照亮比例 f = (1 − cos(λ_月 − λ_日)) / 2
```

再由赤道坐标 + 恒星时换算地平高度角。

**对极限星等的压制**（经验模型）：

```
Δm = (0.35 + 2.6 × f^0.7) × min(1, alt/35)
有效极限星等 = Bortle 基准值 − Δm
```

**对评分的压制**：

```
月影比例 = 窗口内各小时 min(1, alt/30) 的平均（仅计 alt > 0 的小时）
天空分 = 100 × Bortle系数 × (1 − 0.62 × f × 月影比例)
```

**验证时发现的错误**：

原型里原本写的"月龄 18.3 · 23:12 升起"是编的。实际计算 2026-11-07 成都：

| 项 | 原（编造） | 实算 |
|---|---|---|
| 月龄 | 18.3 天 | **28.1 天**（新月前 1.5 天） |
| 月升 | 23:12 | **06:30 左右**（整夜在地平线下） |
| 照亮比例 | 86% | **2%** |

**结论变化**：这一夜根本没有月光干扰，深空窗口从原来的 2 小时（被假月升切断）扩展到 **5 小时**。

> 教训：演示数据不能靠编。天文量必须实算，否则一个假月相就能让整个窗口结论错掉 2.5 倍。

## 6. 数据源与外部服务

### 6.1 三条总原则

1. **天文计算全部在本地完成**——月相、目标高度角、银河、暮光，不上传位置
2. **天气只用境内源**——华为 Weather Kit 为主，和风天气为备，**不接境外源**
3. **数据不出境**——没有境外数据源，隐私政策一句话写完

> 反面教材：天文通 72 个运行时服务里 52 个境外，自建 API 在美西，隐私政策里"境外"出现 0 次。

### 6.5 降级机制

**两级源，四级降级。**

```
L0  华为 Weather Kit        ← 首选
     ↓ 失败
L1  和风天气                ← 备用
     ↓ 失败
L2  本地缓存                ← 兜底
     ↓ 无缓存
L3  仅天文模式              ← 最后防线
```

| 级别 | 数据 | 用户看到 |
|---|---|---|
| L0 | 实时天气 + 天文 | 正常分数 |
| L1 | 实时天气 + 天文 | 正常分数（数据源可在"数据"页查） |
| L2 | 缓存天气 + 天文 | 分数 + **「数据为 N 小时前」** |
| L3 | 仅天文 | **「天气数据不可用」**，不给分数 |

**L3 不给分数**——没有天气就不伪造一个"晴天假设"的分数。

#### 失败的四种判定

| 类型 | 判据 |
|---|---|
| 网络 | 超时（华为 3s / 和风 3s）、连接失败、5xx |
| 鉴权 | 401/403、`1011900001`（能力未开通）、和风 `security restriction` |
| 字段缺失 | 返回里没有 `cloud` 或 `visibility` |
| **数据异常** | 云量 >100 或 <0、能见度 =0、时间戳超 6 小时 |

第四类最容易忽略——**HTTP 200 但数据是垃圾**，比连接失败更危险。

#### 缓存 TTL

| 数据 | TTL |
|---|---|
| 逐小时天气 | 60 分钟（数值预报 6 小时才更新一次） |
| 天文 | 到当天结束（本地算，不需网络） |
| 光污染栅格 | 永久（城市级） |

#### 防雪崩

| 机制 | 策略 |
|---|---|
| 失败冷却 | 某源连败 3 次 → 暂停 10 分钟 |
| 指数退避 | 5s → 15s → 60s |
| 配额保护 | **只在华为失败时才调和风**，不并行请求 |

### 6.6 校准与反馈闭环

#### 6.6.1 为什么需要校准

模式输出的云量本身有误差，且不同源之间差异可达 30%。如果主源存在**系统性偏差**（比如沿海城市普遍偏低 8 个点），分数会整体偏移。

#### 6.6.2 方案 C：离线校准

```
每周一次（后台定时任务）
   ↓
固定 20 个样本城市，同时拉华为 + 和风
   ↓
逐小时对比：Δ = 和风 − 华为
   ↓
统计「系统偏差」
   ↓
写入配置，客户端下次启动生效
```

| 能修 | 修不了 |
|---|---|
| 系统性偏差 | 随机误差（今天的云没算到） |

**样本城市要求**：覆盖不同气候区、不同海拔、不同光污染等级，且固定不变（否则系数每周跳动）。

#### 6.6.3 为什么不实时融合两家

| 理由 | 说明 |
|---|---|
| 定义不同 | 华为给总云量，和风可能是分层合成，平均无物理意义 |
| 不减小误差 | 10% 与 50% 平均成 30%，两边都不对 |
| 配额翻倍 | 和风免费额度撑不住 |
| 无法解释 | "为什么 62 分"→"两家平均"没有说服力 |

**唯一有物理意义的融合是同一份数据内部的分层加权**（低云 0.6 / 中云 0.3 / 高云 0.1），而不是两家数据平均。

#### 6.6.4 用户反馈怎么采集

##### 问什么：问事实，不问主观

| 问法 | 用户答 | 能算出什么 |
|---|---|---|
| ❌「星图准吗？」 | 「还行」「挺准」 | 什么都算不出 |
| ✅「昨晚天空什么样？」 | 少云 | 混淆矩阵 |

**「准不准」是我们算出来的，不是问出来的。**

##### 两个触达通道（不接 Push）

| 通道 | 触发 | 覆盖 |
|---|---|---|
| **A. 次日首次打开 App** | 昨天有窗口 → 底部出现一行 | 主通道，必然触达 |
| **B. 代理提醒** | 次日 09:00 本地通知 | 可选，用户开了才有 |

两个通道加起来接近 100% 覆盖，且**零服务端依赖**。

##### UI 规范：不打断首屏

首屏是「今晚的答案」，反馈不能抢注意力。

| 位置 | 判定 |
|---|---|
| 弹窗 | ❌ 破坏 poster 沉浸感 |
| 首屏中央 | ❌ 挡住数字 |
| **首屏底部一行细字** | ✅ 不遮挡，可划走 |

```
┌───────────────────────────┐
│         （星空照片）        │
│  差                        │
│  观星指数                  │
│  14 /100                   │
│  ☀ ↑07:23  ↓18:11      ⓘ │
│                            │
│ 昨晚 少云 · 记一下？  ×     │  ← 这一行
└───────────────────────────┘
```

点任意一档 → 消失、写入本地、下次联网批量上报。

##### 五档选项

```
全晴 · 少云 · 多云 · 阴 · 没出去
```

**「没出去」这一档很重要**——它是唯一能反映预测可信度的负样本：

> 连续 5 天预测 80 分，用户都没出去 → 要么分数虚高，要么用户不信我们。

##### 频控

| 规则 | 值 |
|---|---|
| 每天最多 | 1 次 |
| 触发前提 | 昨天确实有观测窗口 |
| 连续 3 次「没出去」 | 降频到每周 1 次 |
| 用户点 × | 7 天内不再问 |
| 设置里可永久关闭 | ✅ |

##### 数据链路

```
① 昨天有窗口 → 次日打开 → 底部一行
② 用户点一档 → 本地存 {日期, 城市, 预测分, 实际档位}
③ 攒够 30 条 → 联网批量 POST /v1/feedback
④ 服务端算混淆矩阵 → 输出偏差
⑤ 调整权重 → 下发新 config.json
```

**全程无 Push、无账号、无设备标识。**

##### 唯一值得问的主观问题

放在反馈**之后**，作为辅助信号：

```
「这次预测，你觉得」  偏乐观 · 差不多 · 偏悲观
```

用来验证混淆矩阵的判断对不对，不作为主数据。

#### 6.6.5 反馈怎么变成模型调整

混淆矩阵：

|  | 实际好（晴/少云） | 实际差（多云/阴） |
|---|---|---|
| **预测好**（≥50） | ✅ 命中 | ❌ 虚高 |
| **预测差**（<50） | ❌ 虚低 | ✅ 正确 |

```
虚高率 = 预测好但实际差 / 预测好总数
虚低率 = 预测差但实际好 / 预测差总数
```

| 现象 | 判断 | 动作 |
|---|---|---|
| 虚高率 > 30% | 太乐观 | 云量权重 ↑ 或判好阈值 ↑ |
| 虚低率 > 30% | 太悲观 | 云量权重 ↓ 或阈值 ↓ |
| 两者都高 | 噪声大 | 先查数据源，不是调参能解决的 |

#### 6.6.6 开发期反馈格式

```csv
date,city,score,grade,actual,note
2026-11-07,成都,14,差,多云,
2026-11-08,成都,62,良好,少云,21点后云散了
2026-11-09,冷湖,71,极好,全晴,
```

`actual` 只用四档：`全晴 / 少云 / 多云 / 阴`

**攒够 30 条**即可跑第一版校准。

#### 6.6.7 上报接口（唯一需要的服务端功能）

```
POST /v1/feedback
{
  city_grid: "30.7,104.1",   // 四舍五入到 0.1°，约 11 km
  hour: 2026110721,
  score: 14,
  actual: 3,
  ver: "1.0.0"
}
```

- 无用户 ID、无设备 ID
- 坐标只到 0.1°，无法定位到人
- 不接受自由文本

#### 6.6.8 三阶段样本量

| 阶段 | 来源 | 量级 |
|---|---|---|
| 现在 | 开发者自己（dogfooding） | 每周 3–5 条 |
| 内测 | 10–20 名测试者 | 每周 30–50 条 |
| 上线 | 用户主动反馈 | 每天数百条 |

> **注意幸存者偏差**：愿意反馈的人 ≠ 全体用户，"看到了"的人更愿意反馈。

#### 6.6.9 匿名统计的合规边界

**默认开启，但必须走「匿名统计」路线，不能走「默认勾选同意」。**

##### 两条路的区别

| | 收集个人信息 | **匿名统计** |
|---|---|---|
| 需要同意吗 | 需要，且必须显式 | 不需要，只需告知 |
| 能否默认开启 | ❌ 不能 | ✅ 可以 |
| 监管依据 | PIPL 第 13 条 | 不属于个人信息 |

`《App违法违规收集使用个人信息行为认定方法》`明确列举：

> 以**默认选择同意隐私政策**等非明示方式征求用户同意

**这是红线。** 个人主体被举报，下架 + 影响备案。

##### 做到「真正匿名」的四条硬要求

| 要求 | 做法 |
|---|---|
| 无标识符 | 不传设备 ID / OAID / IMEI / MAC / 用户 ID |
| 坐标粗化 | 经纬度量化到 **0.1°**（约 11 km） |
| 服务端不落 IP | 收到即丢弃，不写日志 |
| 不可关联 | 每次独立，无 session / cookie / 设备指纹 |

上报字段本身：

```
city_grid  "30.7,104.1"    0.1° 网格
hour       2026110721
score      14
actual     3
ver        "1.0.0"
```

**没有任何一项能指向具体的人。**

##### 两个加固措施

| 措施 | 原因 |
|---|---|
| **批量上报**（攒 7 天一次） | 实时上报会让「22:14 在某 11km 网格」近似精确位置 |
| **原始记录 90 天后删除** | 服务端只留聚合结果（各网格平均偏差） |

##### 设置页开关

```
帮助改进观星指数          [● 开]
收集匿名统计，不含个人身份信息
```

**默认开、可关、写清「不含身份信息」**——这三者同时成立才安全。

##### 隐私政策措辞

| ❌ 错误 | ✅ 正确 |
|---|---|
| 我们默认收集您的观星反馈用于改进算法 | 为改进观星指数，本应用会收集**匿名使用统计**：所在城市网格（约 11 公里精度）、预测分数、实际观测情况。**不包含任何可识别您身份的信息**，服务端不记录 IP。您可在「我的 → 隐私设置」中关闭 |

**写了「同意收集您的数据」，默认开就是违规；写成「匿名统计、不含身份信息」，默认开才成立。**

| 风险 | 做法 |
|---|---|

### 6.9 光污染数据与地图叠加

#### 6.9.1 许可排查（重要）

| 数据 | 许可 | 能否商用 |
|---|---|---|
| **Falchi 2016 World Atlas**（GFZ） | **CC BY-NC 4.0** | ❌ **禁止** |
| Lorenz 2022/2025 Atlas | 页面无许可声明 | ❌ 默认保留所有权利 |
| **VIIRS DNB**（NASA/NOAA） | 美国政府作品，**公有领域** | ✅ 可用 |

**结论：只用 VIIRS，自建分级栅格。**

> 这是行业里最容易踩的坑：lightpollutionmap.info 那类服务用的就是 Falchi 数据，直接扒下来商用会侵权。

#### 6.9.2 数据管线

```
VIIRS DNB 年度辐射合成（公有领域）
   ↓ 第 1 步：下载 + 投影到 EPSG:4326
   ↓ 第 2 步：辐射值 → 相对亮度 → Bortle 分档（1–9）
   ↓ 第 3 步：降采样（全球 5 角分 / 中国 1 km）
   ↓ 第 4 步：切片成 256×256 瓦片金字塔
   ↓ 第 5 步：PNG-8 调色板压缩
```

**精度预期**：低于 Falchi（人家用复杂大气散射模型），但**分 Bortle 档位足够**——我们只需要“Bortle 4 还是 Bortle 8”。

#### 6.9.3 瓦片分级

全球 1 km 栅格约 9.3 亿像素，不可全量打包，因此分级：

| 区域 | 层级 | 瓦片数 | 体积 | 存放 |
|---|---|---|---|---|
| 全球兜底 | z=0–5 | 1,365 | ~2 MB | 打包进 App |
| **中国精细** | z=6–9 | ~6,100 | ~9 MB | 打包进 App |
| 境外精细 | z≥6 | 按需 | — | CDN |

**总计约 11 MB**，可接受。

#### 6.9.4 视觉规范

| 做法 | 判定 |
|---|---|
| 彩虹热力图 | ❌ 廉价感，与暖黑体系冲突 |
| **单色暖黄，3 档，低透明度** | ✅ |

```
Bortle 1–3   不绘制（本来是暗的）
Bortle 4–5   暖黄 15% 透明度
Bortle 6–7   暖黄 28%
Bortle 8–9   暖黄 45%
```

**无数据区域全透明**，视觉上自然形成“城市亮、郊外暗”的对比，不用额外的图例。

#### 6.9.5 客户端实现

HarmonyOS Map Kit 提供 `TileOverlay`（瓦片图层，继承 `BaseOverlay`）：

| 项 | 约束 |
|---|---|
| 瓦片尺寸 | 256×256（固定） |
| 图层数 | 建议 ≤ 10 个 |
| 加载方式 | 在线下载 / **本地加载** |
| 模型约束 | Stage 模型 |

调用 `MapComponentController.addTileOverlay()` 叠加，随地图平移、缩放、旋转同步变换。

#### 6.9.6 点查询（比地图更重要）

```
经纬度 → 瓦片编号 → 像素坐标
      → 读 4 邻域 → 双线性插值
      → Bortle 值 → 查表得 mpsas / NELM
```

插值是必须的，否则移动地图会出现方块感。

| Bortle | mpsas | NELM |
|---|---|---|
| 1 | 21.85 | 7.8 |
| 4 | 20.30 | 6.5 |
| 8 | 17.80 | 4.3 |
| 9 | 17.00 | 3.8 |

#### 6.9.7 找暗点（核心功能，优先于地图）

热力图回答“这里有多亮”，**找暗点回答“我该去哪”**。

```
你在这里          Bortle 8 · 极限星等 4.3

往西北 42 km      Bortle 4 · 极限星等 6.5
车程约 50 分钟      ▸ 导航
```

实现：以当前位置为中心，在 100 km 半径内做网格搜索（步长 5 km），取 Bortle 最低点；车程按直线距离 × 1.3 估算。

**主次关系**：

| 位置 | 功能 |
|---|---|
| 首屏 | 一行「最近的暗夜：西北 42 km ▸」 |
| 地图页 | 瓦片叠加（满足“看”的需求） |

#### 6.9.8 实现成本

| 步骤 | 工作量 |
|---|---|
| VIIRS 下载 + 预处理器 | 1 天 |
| 瓦片切片脚本 | 0.5 天 |
| TileOverlay 接入 | 0.5 天 |
| 找暗点网格搜索 | 0.5 天 |
| **合计** | **约 2.5 天** |

### 6.10 关键决策记录

**① 为什么不把评分放服务端**

- 零运营成本、离线可用、位置不出境
- 模型轮次可控——服务端评分随模型更新跳变，实测同一条记录前后差 65 分（85.7 → 20.0）

**② 为什么砍掉置信度（±N）**

置信度需要两个数值模型的分歧，而国内只有华为单模型。引入第二模型要付配额、延迟、可解释性三重成本，收益不明确。

**首屏只给一个数，不给误差范围。** 细节（云量曲线、数据源、新鲜度）放在"数据"页。

**③ 为什么不接境外源**

全球发行不等于必须用境外数据源。华为 Weather Kit 和花瓣地图都是全球服务（境外精度约 1.1 km，对观星完全够用）。

**只用境内源 = 数据不出境 = 合规成本归零。**

**④ 为什么不做实时融合**

见 6.6.3。

## 7. 界面结构

### 7.1 信息架构

```
App 启动
└── 今夜（默认，无上级页面）
    ├── 综合分 + 等级 + 主要限制
    ├── 目标切换：深空 / 行星 / 月面
    ├── 最佳窗口
    ├── 云量曲线 + 窗口带（点任意位置 → 小时详情）
    ├── 三维：云量 / 通透 / 视宁（点击 → 抽屉）
    ├── 月亮 / 极限星等 / 银河
    └── 底部 Tab：今夜 · 七天 · 数据 · 我的
```

### 7.2 首屏：海报式，只有一个数字

参考 Sky Live 的落地页，**整屏就是一张天文摄影 + 一个巨大数字**：

```
┌───────────────────────────┐
│ ☰        成都市         ◎ │
│      11月7日 周五 · 16:42   │
│                            │
│        （星空照片）         │
│                            │
│                            │
│  差                        │
│  观星指数                  │
│  14 /100                   │
│  ☀ ↑07:23  ↓18:11      ⓘ │
│                            │
│ 昨晚 少云 · 记一下？  ×     │ ← 仅次日首次打开时出现
├───────────────────────────┤
│   今夜      七天      我的   │ ← 底部 Dock
└───────────────────────────┘
```

**底部那行是反馈入口**（见 6.6.4），只有“昨天有窗口”时才出现，点任意一档即消失。首屏默认不含它。

**规则：**

1. **首屏只有一个数字**，就是综合观星指数（0–100）
2. **不给任何选择**——没有深空/行星/月面切换，没有模式按钮
3. 底部**有 Dock**（3 项：今夜 / 七天 / 我的），是全局导航；左上 ☰ 只放次级入口
   （选择地点 / 看暗夜地图 / 数据详情 / 使用我的位置）
4. 详细内容（窗口、三维、目标切换、月亮、银河、结露）全部收进右下角 ⓘ

> **修订说明（2026-11-08）**：本条原为"底部没有 tab bar，导航全部收进 ☰"。
> 实施中发现"只有一个数字"不等于"只有一个入口"——七天与我的需要一等入口，
> 否则用户找不到；而 §7.1 的信息架构本来就写了底部 Tab。现统一为：**底部 Dock 三项**，
> ☰ 降级为次级菜单。首屏的极简靠"内容只给一个数字"来保证，不靠"藏掉所有入口"。

**为什么砍掉首屏的选择：**

参考产品的教训是双向的——Sky Live 首屏极简到只有一个数字，用户一眼就有结论；天文通首屏塞了地图、列表、多个入口，新用户不知道看哪。

"深空/行星/月面"是给进阶用户的，藏在 ⓘ 里即可。首屏的默认口径是**深空（当夜最佳目标）**。

### 7.3 无窗口夜

不给"0 分"了事，而要给出口：

```
整夜有云
最近可用  周三 22:40 — 00:50  ›
今晚还能看：月亮 19:20 升起，可拍月面环形山
```

### 7.4 视觉规范

| 项 | 值 |
|---|---|
| 背景 | `#0B0A09`（暖黑，**不是**冷蓝黑） |
| 强调色 | `#FFFFFF`（纯白；原钠灯黄 `#D9A05B` 已按需求弃用） |
| 正文 | `#FFFFFF` |
| 次级文字 | `#CCCCCC` / 三级 `#999999` |
| 分隔线 | `#33FFFFFF`（白色 20%） |
| 卡片 | **不用**。全部用发丝线分隔 |
| 图标 | 线性 SVG，**不用 emoji** |
| 渐变/发光 | **不用** |
| 背景图 | **原图直出**，不做降饱和/加冷色；可读性靠文字阴影，不靠压暗整屏 |

**为什么这些规则**：冷蓝黑 + 多色状态 + 圆角卡片 + emoji + 渐变按钮，是"AI 生成界面"的典型特征组合。

**2026-11-08 修订（二）**：`#0B0A09` 这种"暖黑"（R>G>B）在整屏面积上会被眼睛读成发黄，
已全部换成中性黑 `#0A0A0A`（弹窗 `#121212`），遮罩 ARGB 同步中性化。

**2026-11-08 修订（三）**：`.saturate(0.82)` 与 `#0A14285A` 冷色薄叠**全部移除**——用户要原图效果。

**2026-11-08 修订（一）**：前景统一改为**纯白 + 白色透明度层级**（原先的暖米色与钠灯黄强调色全部弃用）。

### 10.8 通知与提醒

#### 10.8.1 两种通知能力

| 能力 | 接口 | 应用被杀后 | 适合 |
|---|---|---|---|
| **普通通知** | `notificationManager.publish()` | ❌ 不触发 | 应用内的即时提示 |
| **代理提醒** | `reminderAgentManager.publishReminder()` | ✅ **系统代理触发** | 到点提醒观星 |

#### 10.8.2 为什么必须用代理提醒

用户看到「今晚 21:40–00:20 可看」，点「提醒我」，然后**退出 App**。

如果只用普通通知，21:40 什么都不会发生——因为进程已经不在了。

代理提醒是系统级代理：把时间和内容交给系统，由系统在指定时刻拉起通知，**与应用是否运行无关**。

**没有它，窗口提醒等于没做。**

#### 10.8.3 前置条件（三道门）

| 门 | 内容 | 状态 |
|---|---|---|
| ① 权限 | `ohos.permission.PUBLISH_AGENT_REMINDER`（normal / system_grant） | 声明即可，无需 ACL |
| ② AGC 能力 | 开通「代理提醒」，需审批 | ⬜ 待申请 |
| ③ Profile | 能力开通后**必须重新生成 Profile 并手动签名** | ⬜ 依赖 ② |

> ③ 是容易被忽略的坑：能力开通前生成的 Profile 不含该项授权，重签才能生效。

#### 10.8.4 通知授权

代理提醒和普通通知都要先获得用户授权：

```typescript
const enabled = await notificationManager.isNotificationEnabled();
if (!enabled) {
  await notificationManager.requestEnableNotification();
}
```

**没有授权就发不出**，且 `requestEnableNotification` 只能由用户主动操作触发，不能后台调用。

#### 10.8.5 触发时机

| 场景 | 时间 | 内容示例 |
|---|---|---|
| **窗口提醒** | 窗口开始前 30 分钟 | 「今晚 21:40–00:20 可看银河」 |
| **反馈询问** | 次日 09:00 | 「昨晚看到了吗？」五档选择 |

**不做**：

| 场景 | 为什么不做 |
|---|---|
| 云量变化推送 | 需要服务端轮询，违背无后端 |
| 每日例行提醒 | 骚扰 |
| 营销推送 | 不做 |

#### 10.8.6 打扰控制

| 规则 | 值 |
|---|---|
| 每天最多 | 2 条（窗口 + 反馈） |
| 静默时段 | 23:00–07:00 不发（窗口提醒除外，因为那正是要提醒的时候） |
| 用户开关 | 设置页可分别关闭「窗口提醒」「反馈询问」 |
| 连续忽略 | 连续 3 次点掉不理会 → 自动降频至每周 1 次 |

#### 10.8.7 通知文案规范

**一句话，含时间 + 动作 + 关键条件。**

| ✅ 好 | ❌ 差 |
|---|---|
| 今晚 21:40–00:20 可看银河 | 快去看星星吧！✨ |
| 今晚只有 1 小时窗口，银心高度 14° | 今晚观星条件一般哦～ |
| 冷湖今晚极好，还有 3 小时 | 恭喜！今晚是个好天气！ |

规则：

- 不用感叹号
- 不用 emoji
- 不说“恭喜”“快去吧”这类空话
- 数字必须是算出来的，不是估的

#### 10.8.8 实现要点

```typescript
const reminder: reminderAgentManager.ReminderRequestCalendar = {
  reminderType: reminderAgentManager.ReminderType.REMINDER_TYPE_CALENDAR,
  dateTime: { year, month, day, hour, minute },
  title: '今晚可看银河',
  content: '21:40–00:20，银心高度 32°',
  notificationId: 1001
};
await reminderAgentManager.publishReminder(reminder);
```

- 窗口变化时要 `cancelReminder` 后重新 `publishReminder`
- 提醒ID要可追踪（一个观星窗口一个ID）
- 用户取消收藏/换城市时要清理旧提醒

#### 10.8.9 点击提醒后唤起反馈面板

代理提醒的 `wantAgent` **只支持 `pkgName` + `abilityName`，不支持 `uri` / `parameters`**，所以无法直接深链到某个页面。用「本地映射 + 时间匹配」解决。

**① 发布提醒时登记意图**

```typescript
export type LandingIntent = 'window' | 'feedback';

export class ReminderRegistry {
  static async register(reminderId: number, intent: LandingIntent) {
    const p = await preferences.getPreferences(getContext(), 'reminders');
    const map = JSON.parse(p.getSync('map', '{}') as string);
    map[reminderId] = intent;
    await p.put('map', JSON.stringify(map));
    await p.flush();
  }

  /** 找最近 10 分钟内触发的提醒，反查意图 */
  static async resolve(): Promise<LandingIntent | null> {
    const list = await reminderAgentManager.getValidReminders();
    const now = Date.now();
    for (const r of list) {
      const t = triggerTimeOf(r);
      if (now - t >= 0 && now - t < 10 * 60_000) return await this.intentOf(r.notificationId);
    }
    return null;
  }
}
```

**② EntryAbility 落地**

```typescript
onCreate(want: Want) { this.capture(); }
onNewWant(want: Want) { this.capture(); }        // 应用在后台时走这里

private async capture() {
  const intent = await ReminderRegistry.resolve();
  AppStorage.setOrCreate('landingIntent', intent ?? '');
}
```

**③ 首屏用半模态面板弹出**

```typescript
@State showFeedback: boolean = false;

aboutToAppear() {
  if (AppStorage.get<string>('landingIntent') === 'feedback') {
    this.showFeedback = true;
    AppStorage.setOrCreate('landingIntent', '');   // 消费掉，防重复弹
  }
}

build() {
  Column() { /* poster */ }
    .bindSheet($$this.showFeedback, this.FeedbackSheet(), {
      height: SheetSize.FIT_CONTENT,
      dragBar: true,
      showClose: true
    })
}
```

**为什么用 bindSheet 而不是 Dialog：**

| | bindSheet | CustomDialog |
|---|---|---|
| 位置 | 底部升起 | 屏幕中央 |
| 打断感 | 弱，可下滑关闭 | 强，必须点按钮 |
| 适合 | 反馈、选项 | 确认、警示 |

**三层兜底：**

| 情况 | 行为 |
|---|---|
| 映射命中 | 直接弹反馈面板 |
| 映射未命中（提醒被关/超 10 分钟） | 退回首屏底部那行，不弹窗 |
| 用户已反馈 | 不再弹 |

> 即使意图识别失败也不丢反馈，只是从「弹窗」降级成「一行小字」。

**两个坑：**

1. **10 分钟窗口**：用户可能锁屏几小时后才点通知，此时窗口已过，不该再弹——这个判断同时解决识别与过期打扰
2. **状态清理**：`landingIntent` 用完必须置空，否则从后台切回来会再弹一次

**V1 → V2 迁移（2026-11-08 完成）**

最初实现用的是 V1（`@State`），与本文档"V2"的声明不符。已全量迁移：

| 统计 | 数量 |
|---|---|
| `@ObservedV2` 类 | 11 |
| `@Trace` 字段 | 62 |
| `@Local` | 15 |
| `@Computed` | 7 |
| `@ComponentV2` | 1 |
| 残留 V1 装饰器 | **0** |

收益是实打实的：迁移前换城市要在 `applyCity()` 里手工搬 4 次
（`cityName` / `result` / `weekRows` / `darkHint`），现在一句 `this.vm.setCity(i)` 就够，
页面用 `@Computed` 直接读 ViewModel。

需要注意的约束：

- V1 与 V2 **不能混用**，一个组件要么 V1 要么 V2；`@ObservedV2` 的类不能塞进 V1 组件的装饰器。
- `@Local` 必须在组件内初始化，不能从外部传入。
- `@Computed` 只能是纯函数，不能有副作用。
- 数组要触发更新，得靠 `@Trace` 的数组 API（push/splice）或整体替换；元素属性变化要求元素类本身也是 `@ObservedV2`。

**沉浸光感（API 26 系统材质）**

`uiMaterial.ImmersiveMaterial` 是华为的"纯净玻璃光效"，需要 `import { uiMaterial } from '@kit.ArkUI'`
并在 `module.json5` 里加 `metadata: [{ name: "ohos.arkui.UIMaterial.state", value: "enable" }]`。

关键限制（官方文档原文）：**除弹窗、Slider/Toggle/Select 外，其他组件只在
Navigation/NavDestination 标题栏、或横向 Tabs 且 `barPosition: BarPosition.End` 的底部 TabBar 中生效。**

实测（MLR-AL00，`isImmersiveMaterialSupported()=true`，`MaterialLevel=GENTLE`）：

| 尝试 | 结果 |
|---|---|
| 自定义 Dock `Row` 上 `.systemMaterial()` | 无效果（不在生效范围）|
| `Tabs` + 自绘 `tabBar` + `barFloatingStyle` | **进程崩溃**（`barOverlap` 与自绘 tabBar 组合）|
| `Tabs` + `barFloatingStyle`（无 barOverlap）| 不崩溃，但无浮岛 |
| `Tabs` + `BottomTabBarStyle` + `barOverlap(true)` + `barFloatingStyle` | ✅ **玻璃浮岛生效** |

所以底部 Dock 采用第四种。**页面结构也因此改成 Navigation 包裹 Tabs**：
`☰` / `◎` 放进 `Navigation.title()` 的标题栏，才能吃到官方材质（`.systemMaterial(ImmersiveMaterial)`）。

随之调整的两点：

1. 星空图从 `PosterPage` 提到根节点垫底，`Navigation` / `Tabs` / 海报页全部透明，否则标题栏下方会出现黑带。
2. 背景按页切换：只有「今夜」页铺图，七天/我的页铺纯黑，避免标题栏区域出现色带。

不在标题栏里的 `地图` / `i` 仍用 `backgroundBlurStyle(BlurStyle.COMPONENT_THIN)` + 0.5vp 描边。

**底图交叉淡入**：两层 `Image` 叠放——`bgPrev` 垫底不透明，`bgIndex` 从 `opacity 0` 用
`animateTo(320ms, Curve.EaseInOut)` 淡到 1。单层做 `1 → 0 → 换图 → 1` 会中间闪一下底色，双层不会。

**Tab 切换动画**：**不要自己实现**。`Tabs` 自带横向滑动转场，`animationDuration(300)`
就是"当前页向左滑出、新页从右侧滑入"，和官方一致，而且能保住 `barFloatingStyle` 的沉浸光感材质。

尝试过自绘 `Stack` + `if/else` + `transition` 做两段式，动画可控但必须放弃官方 Dock 材质，
已回退。**结论：官方容器自带的转场优先，不要为了动画去换容器。**

**换夜手势**：首屏挂 `PanGesture(Horizontal)`，`|offsetX| > 60` 触发，按方向 `changeNight(±1)` 并轮换底图。
两个坑：①`Tabs` 默认横向滑动会抢手势，必须 `.scrollable(false)`；②一次滑动会多次回调 `onActionEnd`，
需要 400ms 去抖，否则一次滑动跳好几晚。另外底图换成亮图（如蟹状星云）后标题会看不清，
所以顶部再加一层 `#A6000000 → 透明` 的压暗。

**安全区避让**：窗口是 `setWindowLayoutFullScreen(true)`，内容铺到屏边，所以标题栏里的
`☰` / `◎` 会压到挖孔或状态栏。用窗口避让区动态补偿：

```ts
const sys = win.getWindowAvoidArea(window.AvoidAreaType.TYPE_SYSTEM);
const cut = win.getWindowAvoidArea(window.AvoidAreaType.TYPE_CUTOUT);
insetTop   = px2vp(max(sys.topRect.height,   cut.topRect.height));
insetLeft  = px2vp(max(sys.leftRect.width,   cut.leftRect.width));
insetRight = px2vp(max(sys.rightRect.width,  cut.rightRect.width));
```

并监听 `windowSizeChange` 重算——旋转或分屏后挖孔位置会变，只在启动时算一次就会重新重叠。

**Dock 实现说明**：先试 `Swiper + SwiperController.changeIndex`，点击「我的」只前进一页（0→1），
再试官方 `Tabs`：`vertical(true)` 会把 tab 栏甩到屏幕右侧，横向 Tabs 的 `onChange` 在启动时
连发 1→0→2→1→0。最终改用 **Stack + 自绘 Dock**，`pageIndex` 单值驱动，点击即切、状态确定；海报页另挂 `PanGesture(Vertical)` 恢复「上滑进七天」。

**坐标系决策**：中国大陆地图按 GCJ-02 显示，天文/光污染计算必须用 WGS-84。
规则是「存储与计算一律 WGS-84，进地图前才转换」。
`core/geo/Coord.ets` 实现了 WGS-84→GCJ-02，实测与官方 `map.convertCoordinateSync`
结果完全一致（dLat=dLon=0.000000）。

**定位决策（两档渐进）**：位置只用于查天气、算天体高度、估算光污染。

- **第一档 城市级**：`APPROXIMATELY_LOCATION`，`getLastLocation()` 缓存位置**秒出分数**，不用等 GPS。
- **第二档 精确**：`LOCATION`，与第一档**同时申请**，用户可在系统弹窗里单独关闭"精确位置"。
  拿到后异步 `getCurrentLocation({priority: ACCURACY, maxAccuracy: 50})` **静默更新**，失败不打断。
- **精度可见**：数据页显示「成都市 · ±14 m」或「城市级」，让用户看得见精确定位是否生效。
- 不申请后台定位、不涉及 ACL。拒绝任一档都自动降级，功能不受影响。

**为什么值得申请精确**：天气预报网格 5–10 km、天体高度角 0.1°≈11 km，这两项城市级就够；
真正吃精度的是**光污染等级**与**到暗夜地点的距离**——前者等 VIIRS 栅格接入后才用得上，
后者现在就能受益（86 km → 86.3 km）。

**地图只负责展示**（`setMyLocationEnabled` / Marker），坐标源始终是 Location Kit。
地图有常驻入口（首屏右下「地图」），不再只挂在低分夜的暗夜提示上；
无暗夜站点时以城市为中心、不落标记。

**关于地图能力的更正**：此前判断「Profile 里 `allowed-acls` 为空 → 地图能力没生效」是**错的**。
`allowed-acls` 只记录**受限权限（ACL）**，与开放能力无关。开放能力在 Profile 的
`app-services-capabilities` 字段里。实测旧 Profile 已含 `com.huawei.service.mapkit`，
地图一直可用，缺的只是地图 UI。

## 附录 A：日落辉光模型（天文通实测）

虽然不在"今夜星"范围内，但这是目前市面上少见的、有真实工程价值的功能，记录备查。

### A.1 时间窗口

| 纬度 | 峰值太阳高度角 | 窗口时长 |
|---|---|---|
| 19.2° | −0.74° | 45 分 |
| 39.9° | −1.02° | 45 分 |
| 60.0° | −0.73° | 45 分 |

- 峰值固定在 **太阳高度角 −0.73°**
- 窗口固定 **45 分钟**：日落 `[峰值−15min, 峰值+30min]`，日出镜像

### A.2 气溶胶评分

```
AOD ≤ 0.25        → 1.00
0.25 < AOD < 0.33 → 线性降到 0.50
AOD ≥ 0.33        → 0.50（地板）
```

色带：`<0.10 crystal_clear` / `0.10–0.25 warm_clear` / `0.25–0.50 warm_hazy` / `>0.50 murky`

### A.3 触发条件

**低云 < 25% 且 中高云 > 15%**（89% 准确率）

物理含义：低云挡住地平线就看不见，中高云才能接住夕阳。

### A.4 强度不可还原

指数与小时级云量相关性仅 −0.28 ~ +0.18；实测"太阳方位 60km"相关 +0.475，"反方向 60km"反而 +0.662。结论：**该模型没有实现方向性，只是区域云量的粗略函数**，不值得复刻。

### 12.2 P0：把假数据换成真数据

目前 `TonightViewModel.demoDay()` 返回硬编码常量：

```ts
d.transp = 0.72;  d.seeing = 2.1;  d.aod = 0.15;
const clouds = [8, 6, 10, 14, 18, 24, 30, 36, 40, 44, 42, 38, 34];
```

**后果：分数天天一样，换城市只有 Bortle 变。** 指数地图在此之上做出来也是假的。

#### B1 天气数据接入（✅ 2026-11-09 完成）

**结论：和风天气单源，境外兜底已关闭（`ALLOW_FOREIGN = false`）。**

| 项 | 实现 |
|---|---|
| 逐小时 | `/v7/weather/24h`，取 17:00–06:00 |
| 空气质量 | `/airquality/v1/current/{lat}/{lon}`，AQI 推通透度与 AOD |
| 露点 | 和风直接给 `dew`，不再靠 Magnus 估算（无该字段时回退公式）|
| 缓存 | 30 分钟，按 0.1° 网格 |
| 降级 | 和风 → 缓存 → 无预报（界面明示）|

**两个已知妥协**：

1. **没有能见度**：24h 接口不返回 `vis`，通透度改由 `AQI + 湿度` 推算
   （`transp = 1 − min(0.5, aqi/400) − max(0,(hum−70)/30)×0.3`）
2. **没有分层云量**：和风只给总云量，因此 B4 落定为**方案 A**——
   分层逻辑留在代码里当接口，实际数据下退化为"整层计入低云"（保守，因为低云最伤）

#### 原计划

| 项 | 内容 |
|---|---|
| 主源 | **和风天气**（专属 Host `mn6hf38tay.re.qweatherapi.com`）|
| 说明 | 华为 Weather Kit **仅系统应用可用**，已排除 |
| 备选 | 彩云天气 / 心知天气（境内，需另备凭据）|
| 降级 | 和风 → 缓存 → 仅天文 |
| 映射 | `cloudCover→cloud`、`visibility→transp`、`humidity+温度→露点`、`AQI→aod 粗替` |
| 缓存 | 30 分钟，按坐标 0.1° 网格分桶 |

**必须做的降级**：无网/超时时界面要标「无预报」，不能默默给一个分数。

#### B2 风速进评分

现状：**完全没有风速项**。物理依据：

| 风速 | 影响 |
|---|---|
| > 8 m/s | 长曝光开始抖，赤道仪跟不上阵风 |
| > 12 m/s | 遮光罩/导星镜被吹振，深空基本废 |

权重调整（新增 10%，从云量挪）：

```
现在：云 0.55 · 通透 0.20 · 视宁 0.15 · 露点 0.10
改后：云 0.50 · 通透 0.18 · 视宁 0.13 · 露点 0.09 · 风 0.10
```

#### B3 降水硬否决

**不是加权，是一票否决。** 窗口内有雨/雪/雷电 → 分数直接归零，文案「今夜有雨，不宜出门」。

反面做法：`0.05 × (1−降水)` 会让 30 分变成 28 分，等于没说。

### 12.8 下拉刷新与限流（2026-11-09）

首屏用系统 `Refresh` 组件实现下拉，加载动画是华为原生样式。

**限流规则**（天气 API 按次计费，必须克制）：

| 规则 | 值 | 原因 |
|---|---|---|
| 冷却时间 | **5 分钟** | 天气 30 分钟内基本不变，刷新没有意义 |
| 每日上限 | **12 次** | 保护和风免费配额（1000 次/天）|
| 持久化 | preferences | 重启 App 不能重置 |

命中限流时：加载动画立即停止，顶部提示「刚更新过 · N 分钟后再试」或「今天刷新次数已用完」，2 秒后自动消失。

**已知取舍**：系统 `Refresh` 会先启动动画再回调，所以被限流时会闪一下再停。想彻底避免需要 `enableRefresh(false)`，
但那样用户按了没反应，反而更困惑——选择保留提示。

### 12.9 系统能力评估：实况窗 / 闪控球 / 闪控窗（2026-11-09）

三个能力查过官方文档后结论不同，**只有闪控窗值得做**。

| 能力 | 起始版本 | 权限 | 场景限制 | 结论 |
|---|---|---|---|---|
| 实况窗（Live View Kit）| HarmonyOS 5+ | 需开通推送 + 实况窗权益（AGC 审核）| **15 类场景白名单** | ❌ 不申请 |
| 闪控球（FloatingBall）| API 20 | `USE_FLOAT_BALL`（受限权限，AGC 审批）| **仅 6 类场景，且违规有处罚** | ❌ 不申请 |
| 闪控窗（FloatView）| **API 26** | `FLOAT_VIEW`（user_grant，走运行时授权）| 文档未列白名单 | ✅ 待做（B14）|

#### 实况窗为什么不行

官方场景表只有：TAXI / DELIVERY / FLIGHT / TRAIN / QUEUE / PICK_UP / SCORE / RENT /
TIMER / SUBSCRIBE_TIMER / WORKOUT / NAVIGATION / CHECK_IN / EXPRESS / PROGRESS / TRADE。

准入门槛还要求「用户非常关注、**需要反复查看**」——观星指数看一次就够，不满足。
最接近的 TIMER 明确排除「事项待办、日程提醒」，而观星窗口提醒正好属于这一类。

> 被拒会留档，可能影响后续 ACL 申请，不值得试。

#### 闪控球为什么不行

官方原文：

> 当前仅对跨应用的**题目搜索、账单记录、商品比价、抢单、翻译**场景，
> 以及**金融类应用的实时盯盘**场景开放此权限。
> 接入后需在以上场景范围内使用，否则将会进行相关处罚与限制。

观星不在六类之内，硬上等于违规。

#### 闪控窗为什么可行

- 只要 `ohos.permission.FLOAT_VIEW`，是 **user_grant**（声明 + 运行时申请），不走 AGC 审批
- 文档只举例「股市盯盘、直播」，**没有写白名单和处罚条款**
- 单应用一个窗口，可由闪控球绑定切换（但我们不做闪控球，用独立闪控窗）

规划的小窗内容：

```
┌──────────────┐
│ 今夜星        │
│  16  · 云 95% │
│ 窗口 21:00    │
└──────────────┘
```

场景：晚上在楼顶，手机开着星图 App，角落浮一个小窗盯云量和窗口时间，不用切回今夜星。

**前置条件**：设备需 HarmonyOS 6.x（API 26）以上。开发平板 MLR-AL00 满足。

**实现要点**（据官方文档）：

1. 声明 `ohos.permission.FLOAT_VIEW`，`requestPermissionsFromUser` 申请
2. `floatView.create({ context, templateType: ROUNDED_RECTANGLE })`
3. `setUIContext('pages/FloatViewPage')` 指定小窗内容页
4. `getFloatViewLimits()` 取推荐尺寸 → `setWindowSize()`
5. `start()` 启动；只允许应用在前台时创建

**待定**：小窗显示哪些字段（分数 / 云量 / 窗口时间 / 银河指数）。

### 12.10 银河指数（红针）（2026-11-09）

表盘红针从「昨晚」改成「银河指数」——两个分数意义不同，不能混用同一根针。

**为什么不能只看银心**

第一版用银心（17.76h / −29°）判断，结果冷湖（Bortle 1）算出银河 0：
11 月一到晚上，银心已经落到西边了。但冬季银河（猎户座—大犬座段）照样横在天上。

改为取银道面四个代表点的**最高高度角**：

| 代表点 | 赤经/赤纬 | 主导季节 |
|---|---|---|
| 银心（人马座）| 17.76h / −29° | 夏季 |
| 天鹅座 | 20.70h / +42° | 夏季 |
| 仙后座 | 1.00h / +60° | 秋季 |
| 猎户座 | 5.59h / −5° | 冬季 |

**四项因子**

```
银河 = 100 × 高度角分 × 月光分 × 光污染分 × 云量分
```

系数集中在 `MwTuning`（`core/score/Score.ets`），改这里不用动算法结构：

| 常量 | 值 | 含义 |
|---|---|---|
| `ALT_MIN` | 10 | 低于此高度角判不可见 |
| `ALT_SPAN` | 55 | 再升高多少度到满分 |
| `MOON_UP` | 0.75 | 满月在天上砍 75% |
| `MOON_DOWN` | 0.15 | 满月在地平线下砍 15% |
| `BORTLE_ZERO` | 9 | Bortle 9 归零 |
| `BORTLE_SPAN` | 6 | 往下 6 级到满分 |
| `CLOUD_ZERO` | 100 | 云量 100% 归零 |

**可解释**：数据页显示四项分解，

```
银河指数 12
高度 15° × 月光 1.00 × 光污染 0.67 × 云 0.99
```

用户能自己乘回去，和我们复现的分数对齐——这是评分产品建立信任的前提。

**待校准**：目前数值偏保守（拉萨 Bortle 5 只给 12）。若反馈说偏低，
把 `ALT_MIN` 调到 5、`ALT_SPAN` 调到 40，同样高度角下分数约翻倍。
